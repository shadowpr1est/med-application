# SmartMed: backend и продуктовые workflow

Документ описывает целевой первый релиз: адаптивное PWA на Netlify, Firebase Authentication, Firestore, Storage, Cloud Functions, Cloud Tasks и FCM Web Push. Это приложение помогает вести расписание и пользовательские отметки; оно не назначает лечение и не подтверждает факт проглатывания лекарства.

## 1. Аккаунт и жизненный цикл данных

### Гость

1. При первом запуске пользователь может продолжить локально без регистрации.
2. Профиль, расписание, отметки и небольшие фото сохраняются в браузере.
3. Пользователь может скачать локальную копию JSON. Фото, сохранённые только в Firebase Storage, в этот файл не входят.

### Регистрация и вход

1. Email и пароль обрабатывает Firebase Authentication; пароль не пишется в SmartMed.
2. При регистрации локальные записи загружаются в новый аккаунт.
3. При входе загружается облачный профиль. Если Firebase Auth-сессия восстановилась после перезапуска браузера, SmartMed повторно загружает облачное состояние.
4. Доступна отправка ссылки для сброса пароля.
5. Перед выходом незавершённая облачная запись отправляется; после успешного выхода локальная копия очищается, облачная остаётся.

### Удаление аккаунта

1. Пользователь открывает «Удалить аккаунт», вводит пароль и подтверждает действие.
2. Клиент повторно подтверждает пароль в Firebase Auth; callable function требует свежую авторизацию.
3. Backend ставит флаг удаления, отменяет доступные задачи уведомлений, удаляет файлы под `users/{uid}/`, рекурсивно удаляет Firestore-поддерево и удаляет Auth-пользователя.
4. Повторный запрос безопасен для уже удалённых файлов/документов; фактическая ошибка удаления должна быть показана пользователю и обработана повтором.

## 2. Схема Firebase

```text
users/{uid}
  profile fields, schemaVersion, syncRevision, cloud write lease
users/{uid}/medications/{medicationId}
users/{uid}/scheduledDoses/{doseId}
users/{uid}/settings/current
users/{uid}/trustedContacts/current
users/{uid}/devices/{deviceId}
users/{uid}/notificationEvents/{eventId}   # запись только backend
users/{uid}/dose-photos/{photoId}          # Firebase Storage
```

Пользователь может обращаться только к `users/{свой uid}/...`. События доставки создаются backend и доступны владельцу только для чтения. Фото приватны, ограничены владельцем и типом/размером файла.

`ScheduledDose` хранит дату, местное время, UTC-время, статус подтверждения, версию задач, отметку и путь к фото. Состояние уведомления отдельно хранится в `NotificationEvent`: постановка, обработка, отправка, ошибка, повтор и отмена не меняют смысл пользовательской отметки.

## 3. Лекарство и приём

1. Создание лекарства задаёт название, дозировку, единицу, локальные времена, дни недели и даты курса.
2. Генератор создаёт отдельные `ScheduledDose`; редактирование пересоздаёт только будущие неподтверждённые приёмы.
3. Допустимые пользовательские переходы: `scheduled → reminded → confirmed` либо `scheduled/reminded → skipped` по явному действию.
4. «Скоро» и «подтверждение отсутствует» сейчас вычисляются для экрана по времени, а не являются отдельным подтверждённым медицинским фактом.
5. Подтверждение — только отметка пользователя. Фото остаётся необязательным по настройке; его можно посмотреть или удалить, оставив событие истории.
6. Удаление/пауза лекарства не стирает уже подтверждённую историю.

До production остаётся формально выбрать окно «скоро», порог просрочки, поведение после окончания курса, смену часового пояса и правила хранения событий.

## 4. Уведомления и эскалация

1. Firestore trigger замечает новую или изменённую дозу, повышает `notificationVersion` и ставит Cloud Task на индивидуальное время.
2. Cloud Tasks планирует максимум примерно на 29 дней вперёд; ежедневная функция добавляет события в доступное окно.
3. Повторные напоминания и контактные эскалации читают актуальные настройки.
4. Перед отправкой транзакция повторно проверяет владельца по пути документа, статус дозы, версию и отсутствие удаления аккаунта.
5. `NotificationEvent` получает idempotency ID и короткую lease-блокировку. Firebase retries повторяют ошибочную доставку, не создавая новый логический event.
6. Push не включает название лекарства или дозировку. Email контакту сообщает лишь, что отметка о приёме не появилась, и просит связаться с пользователем.
7. Email идёт через Resend только при включённом контакте и зафиксированном согласии. SMS автоматической доставки пока нет.

Повторная проверка непосредственно перед внешним провайдером уменьшает риск устаревшей отправки, но не делает внешнюю доставку атомарной с Firestore. Неоднозначный сетевой ответ требует явных сценариев дедупликации и проверки на эмуляторе/тестовом провайдере.

## 5. Синхронизация между устройствами

1. Каждая локальная правка сразу сохраняется на устройстве и ставится в очередь облачной синхронизации.
2. Backend revision и краткоживущая блокировка предотвращают незаметную запись устаревшего полного снимка другим клиентом.
3. При конфликте приложение оставляет локальные правки и предлагает загрузить облачную версию либо явно записать локальную поверх неё.
4. При восстановлении сети синхронизация повторно ставится в очередь.

Текущий клиент отправляет коллекции пакетами, а не одной атомарной транзакцией. Сбой посередине большого набора может оставить частично применённый снимок; для production лучше перейти на серверный sync API или атомарную версионированную публикацию снимка с tombstone-записями. До этого момента ограничения размера набора и обработку частичного сбоя нужно проверить на эмуляторе.

## 6. Настройки

- Часовой пояс берётся из устройства; каждое событие хранит локальную и UTC-дату.
- Повторы имеют общий интервал и количество; контактная эскалация имеет отдельную задержку.
- Подтверждение без фото можно включить/выключить.
- Канал доверенного контакта: email поддерживается backend; SMS доступно только как локально подготовленное сообщение. При включённом облачном email workflow нельзя сохранить автоматическую SMS-эскалацию.
- Отзыв браузерного разрешения отключает локальные уведомления. Web Push требует HTTPS, зарегистрированного service worker и токена устройства.

## 7. Проверенные изменения текущего этапа

- Основной интерфейс и PWA-иконка приведены к синей палитре референса.
- Модальные окна закрываются крестиком, кнопкой отмены, нажатием на фон и клавишей Escape; фокус возвращается к исходной кнопке, камера останавливается при закрытии.
- В форме лекарства устранено горизонтальное переполнение на узком экране.
- Добавлена кнопка съёмки для камеры, проверка файла, сжатие фото и обработка ошибок камеры/чтения.
- Фото из истории открывается и удаляется отдельно от записи приёма.
- Добавлены настройка подтверждения без фото, сброс пароля и защищённое удаление облачного аккаунта.
- Cloud sync использует revision, lease и явное разрешение конфликта вместо молчаливой перезаписи.
- Cloud Tasks проверяют актуальность дозы/версии транзакционно; сборщик расписаний берёт владельца из пути Firestore.

## 8. Production gates

В репозитории нет Firebase/Netlify проекта и секретов. До реального запуска остаются: Emulator Suite для Auth/Firestore/Storage/Functions; тесты правил изолированных аккаунтов; проверка частичного sync, гонок и повторных доставок; App Check; резервные копии/мониторинг; подтверждённый Resend sender и пробные email; HTTPS-домен и Netlify deploy preview. Также нужны согласованные тексты приватности, согласия, хранения/удаления и поддерживаемых стран/языков. PWA не является нативным Flutter-приложением.
